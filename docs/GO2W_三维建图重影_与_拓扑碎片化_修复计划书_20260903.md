## 1. 通俗解释

### 1.1 三维地图为什么"叠在一起"

把建图想成**用一台相机拍很多张照片，然后按拍照时的位置把它们拼成一张全景图**。

拼得对不对，完全取决于"我以为我站在哪"这个记录准不准。机器狗原地转向时，激光雷达 + IMU 算出来的位置会**偏一点**（实测原地转 30° 会误报 0.05–0.5 米的平移）。偏一点不要紧，问题是：

1. **这台"相机"从今天 11:29 开机后就一直没关过，已经开了 5 小时 43 分钟。** 它把这 5.5 小时里拍的 21 张照片**全部**留着，每次给你看的全景图都是这 21 张一起拼。其中 12:26 那两张是在系统崩坏期拍的——那会儿位置估计一路飞到 11 公里外。你后来改了多少次参数都没用，因为**没人把这台相机关掉重开，它手里还捏着那些烂照片**。

2. **拼图用的"对齐"功能被设成了 1.5 米的容差。** 意思是：找对应特征时，1.5 米范围内长得像的都算同一个东西。可室内点云的分辨率是 0.15 米——**1.5 米范围里能装十条墙缝，它随便挑一条就对上了**。参数文件里其实已经写了一整段话说明"必须改成 0.5 米"，但**只写了说明，数字没动**。

3. **本来有个"回环"机制能救**：转一圈回到原朝向时，认出"哦这面墙我见过"，然后把中间累积的误差一次性拉平。但它找"我见过的地方"时，只挑**空间上最近的 10 个关键帧**——原地转向时所有关键帧都挤在半米内，挑到的 10 个全是刚刚才拍的，**它们和当前帧犯的是同一个错，互相印证不出任何问题**。

4. **而且它记性太短**：每转 20° 存一帧，只保留最近 15 帧。转一圈需要 18 帧——**还没转完一圈，起点那一帧就被忘掉了**，等你转回原位，它已经不记得原来的样子，认不出来。

结果就是：同一块地板被画成了**厚 1.15 米**的一层"果冻"（单帧只有 0.53 米，多出来的全是拼歪的）；同一面墙有好几个副本；地图高度方向比单帧多出 2.74 米——**机器狗从来没上下移动过，这 2.74 米凭空多出来的厚度就是"叠"**。

### 1.2 拓扑图为什么碎成一堆小块

拓扑图的作用是：告诉机器狗"垃圾桶在办公桌旁边，办公桌在这个房间里，从这个房间往北能到走廊"——这样它才能推理路线。

现在的做法出了两个岔子：

1. **物体之间的连线只来自"同一张照片里看到的两个东西"。** 视觉大模型看一张图，能说"垃圾桶在办公椅左边"。可它**看不到上一张照片**，所以永远说不出"这张照片里的椅子，就是上一张照片里桌子旁边那把"。于是每转一个视角就产生一组物体，**组内互相连着，组和组之间一根线都没有**。转 3 次视角 = 3 个孤岛。实测正是 3 个孤岛，大小 14 / 6 / 6 个物体。

2. **本来有一根线能把孤岛连起来，但被扔了两次。** 后端其实记录了"这个物体是从 P1 这个地点看到的"（`OBSERVED_FROM`，实测 216 条边里就有这类）。只要把地点当成一个中转站，所有视角看到的物体就都挂在同一个中转站上，自然连成一张大图。可是：
   - 后端做给网页看的那份投影里，**只放物体、不放地点**；
   - 前端又写了一行 `OBSERVED_FROM: 1` 把这类线**明确列为"不是物体关系"直接过滤掉**。

   两道关卡一起，把唯一的桥拆了。

3. **雪上加霜：地点自己也碎了。** 代码里本来有一道保护——"轮子没走，就不算换了地方"，专门防止原地转向被误判成移动。可**调用它的地方从来没把轮子走了多少传进去**，这道保护一次都没生效过。加上今天下午把转速从 0.15 提到 1.0 rad/s 之后，转向时的姿态补偿让机体每转 30° 真实前进约 0.1 米——转半圈就绕出 0.42 米，超过了"0.35 米就算换地方"的门槛。于是原地转一圈会凭空生出 2–3 个地点。**慢转时轮子每段只走 0.006 米，从不触发——所以这个问题是提速之后才出现的。**

结果就是：本来该是"一个房间 + 26 件家具挂在上面"的一张连通大图，变成 3 个互不相连的小块，而且同一把办公椅在不同块里被当成不同的椅子重复登记。这种小块确实**对辅助导航没有用**——用户的判断是对的。

## 2. 实机证据（2026-09-03 16:50–17:10 实测，可复现）

### 2.1 判据的选取理由

**不要用"地图 extent 变大"当重影证据**——机器狗转向看到更多空间，extent 本来就会变大。
本计划采用**转向不可能改变的物理量**：

- 地板/天花板的真实高度不随转向改变 → **Z 方向的厚度**是干净判据；
- 机器狗从未垂直移动 → **地图 Z extent 不该显著超过单帧 Z extent**。

## 3. 根因逐条（现象 → 代码位置 → 机制 → 证据）

### A. SLAM 位姿图跨会话从不清空【最直接，解释"为什么改了很多次还是叠"】

**代码位置**

- `ros2_ws/src/plain_slam_ros2/src/slam_3d_node.cpp:52-53`
  ```cpp

  slam_.ClearSLAMDataDir();   // ← 只在节点构造时调用一次
  ```
- `ros2_ws/src/plain_slam_ros2/src/slam_3d_interface.cpp:352-368`
  ```cpp

    filtered_map_cloud_.clear();
    for (int i = pose_graph_.size() - 1; i >= 0; --i) {   // 全部关键帧
      const Sophus::SE3f& T = pose_graph_[i];
      PointCloud3f cloud; ReadPointCloud(filtered_cloud_file, cloud);
      for (const auto& p : cloud) filtered_map_cloud_.push_back(T * p);  // 按各自位姿堆叠

  ```
- `scripts/go2w/start_plain_slam_mapping.sh` —— 全文 218 行，`grep -n 'pkill|rm -rf'` **零匹配**，
  只有 `:141 setsid bash -c 'exec ros2 launch go2w_plain_slam_bridge plain_slam_go2w.launch.py'`
- `scripts/go2w/start_autonomous_search_web.sh:153` —— `/go2w/slam/aligned_scan` 有 publisher 就跳过启动

**机制**：地图 = 全部关键帧 × 各自位姿。位姿图只在**进程新建**时清空，而两个启动脚本都不重启它。
所以每次"改配置后重启"，实际重启的是 bridge / WebUI / relay，**SLAM 从来没被重启过**，
新参数只影响新增关键帧，旧的 21 帧（含发散期）继续每帧被堆进地图。

**为什么 WebUI 的健康门没拦住**：`mapping_session_id` / `session_start_stamp` 这道门只比较**消息 stamp**，
而 `map_3d` 的 stamp 永远是当前时刻 → 门认为"这是新数据"。
它拦不住"**新消息里装着旧漂移点云**"这种情况。这是判据设计的盲区，不是门坏了。

**证据**：§2.3（进程 5h43m + filtered_cloud 跨 5.5 小时）、§2.4（`rejected_counts {}` 一次没拒）。

### B. 两个 LIO 参数写了 rationale 但没落值

**代码位置**：`configs/go2w/plain_slam_lio_params.yaml`


`git diff configs/go2w/plain_slam_lio_params.yaml` 的 `@@ -7,9 +7,20 @@` **全部落在注释块内**，参数本体一个字没变。
注释自己写的理由：「1.5 m 关联半径在 filter_size 0.15 的室内点云里会把同一面墙不同位置的点错配到一起；

**机制**：1.5 m ÷ 0.15 m = 10 倍体素，同一面墙上相隔 1.5 m 的两个点会被当成同一特征 →

积分出的位移系统性偏大。两者叠加就是转向时的假平移。

**注意**：生成器不改这两个值——`grep -n 'max_correspondence_dist\|acc_scale' scripts/go2w/generate_plain_slam_pandar_config.py`
**零匹配**，它原样搬运。所以 `runtime/go2w/plain_slam/generated_lio_3d_params.yaml` 里也是 1.0 / 1.5，
**改完源头必须重新生成**。

### C. 回环在原地转向场景下结构性失效

**代码位置**

- `ros2_ws/src/plain_slam_ros2/src/slam_3d_interface.cpp:421-439` `GetTargetCandidateIndices()`：
  关键帧数 > `max_num_loop_candidates_` 时，用 nanoflann **KNN 按 3D 位置**取最近 N 个作候选。
- `slam_3d_interface.cpp:199-204`：
  ```cpp
  const size_t didx = latest_idx - target_indices[i];
  if (didx > max_num_loop_candidates_) gicp_.SetHuberDelta(orig_huber_delta * 10.0f);
  ```
- `configs/go2w/plain_slam_slam_params.yaml`：
  ```yaml
  loop_closure:
    num_loop_candidates: 10
    gicp_max_correspondence_dist: 3.0
  ```

**机制（两层失效）**

1. 原地转向时全部关键帧挤在半米内 → KNN 取到的 10 个**全是刚建的时序邻帧**。
   邻帧与当前帧共享同一份累积漂移，配准残差很小 → **看起来"没问题"，纠正力为零**。
   真正需要闭合的是"一圈之前那一帧"，但它在空间上和邻帧一样近，**排不进前 10**。
2. `:199-204` 那个"远期候选放宽 huber"的补偿分支，因为 KNN 早就把远期候选筛掉了，**基本走不到**。
3. 即使侥幸产生回环边，`gicp_max_correspondence_dist: 3.0` 比 LIO 的 1.5 更离谱 →
   **回环边本身就是错的**，加进位姿图只会把地图拧得更歪。

### D. LIO 局部地图的记忆短于一圈

**代码位置**：`configs/go2w/plain_slam_lio_params.yaml`

```yaml

  angle_th: 20.0        # 每转 20° 建一个关键帧 → 转一圈 360/20 = 18 帧
```

且这个漂移**没有任何机制能事后纠正**（因为 C 也失效了）。

### F. Place 自身碎片化：保护写好了但接线没接上

**代码位置**：`app/spatial/place_graph.py:128-171`

```python
def _resolve_place(self, *, pose, observed_displacement_m):
    current = self.places[self._current_place_id]
    # Independent wheel motion is the primary relocation evidence.  A
    # turn-only cycle may contain a badly drifting LIO pose; never let
    # that pose create P2/P3 while the wheels report no translation.
    if observed_displacement_m is not None:          # ← 永远是 None，此分支从未执行
        if observed_displacement_m < self.relocation_min_displacement_m:   # 0.10
            return current.place_id, False, False
        ...
    if pose is not None:                             # ← 实际走这条
        nearest_id, distance = self.nearest_place_id(pose)
        if nearest_id is not None and distance <= self.merge_distance_m:   # 0.35
            ...
        new_id = self._new_place(pose=pose, from_place=self._current_place_id)  # ← 建新 place
        return new_id, True, False
```

**断链点**：`app/live_robot/autonomous_explorer.py` 里两处 `update_observation` 调用
（`:547` 目标确认路径、`:1087` `_update_memory`）**都不传 `observed_displacement_m`**；
`grep -n displacement app/live_robot/autonomous_explorer.py` **整文件零匹配**。

**为什么今天才暴露**：`get_pose()` 返回的是**轮式里程计**，不是 LIO
（`app/navigation/go2w_experimental_backend.py:135-147`，`source="wheel_fused_odom"`）。
转速从 0.15 提到 1.0 rad/s 后，`turn_longitudinal_compensation_vx=0.05` + `post_turn_rollback`
让每段 30° 真实推进约 0.098 m、wheel 记 **0.1117 m** → 原地转向变成**绕直径约 0.42 m 的小圈**，
转到约 180° 时离起点超过 `merge_distance_m=0.35` → 建新 place。
慢转（0.15 rad/s）时每段仅 **0.0060 m**，从不越界 —— **所以碎片化是提速之后才出现的**。

**关键提醒**：`0.1117 > relocation_min_displacement_m=0.10`，
**光把 `observed_displacement_m` 传进去也拦不住**。所以 §4 阶段 2 选的是改 `merge_distance_m`。

**没有配置注入点**：`app/spatial/semantic_navigation_graph.py:34`
`self.place_graph = place_graph or PlaceGraph()` —— 无参构造，
`merge_distance_m=0.35` / `relocation_min_displacement_m=0.10` 是 `place_graph.py` 里的**硬编码默认值**。
（`configs/go2w/rgbd_spatial_exploration.yaml:19 merge_distance_m: 0.25` 是 `SemanticObjectMap` 的参数，**不是这个**，别改错。）

## 7. Trade-off：转速 1.0 rad/s 对建图的影响（**由用户决定，不擅自回退**）

**事实两面，都摆出来：**

| 面向 | 证据 |
|---|---|
| 快转**有利** | G4.2 实测：提速后打滑消失，wheel 真滚，pslam/wheel 位移比值从 **7.80** 回到 **0.878**。慢转（0.15 rad/s）时轮子几乎不转、里程计几乎不动，LIO 与 wheel 完全对不上 |
| 快转**不利** | 角速度大 → 去畸变与逐帧配准更难；且它是根因 F 的**触发因素**（每段 30° 真实推进 0.098 m，绕出 0.42 m 小圈） |

**三个选项，请用户选一个：**

- **选项 1（默认，推荐先试）**：保持 1.0 rad/s。阶段 1 的 B/C/D 直接针对配准与回环，
  阶段 2 的 `merge_distance_m 0.6` 覆盖 0.42 m 小圈。**先按现状验收，不动转速。**
- **选项 2**：建图阶段降到 0.5 rad/s，搜索阶段保持 1.0。折中，但引入"两套转速"的状态，
  需要额外区分逻辑（轻微违反禁止过度设计）。
- **选项 3**：整体降到 0.5 rad/s。配准更容易、小圈更小，但要重新验证打滑是否回来
  （G4.2 的 7.80 比值可能重现）。

**AI 执行本计划时：默认选项 1，不要擅自改转速。** 若 §5 阶段 1 判据在 1.0 rad/s 下不通过，
**如实报告并把选项 2/3 交回用户决定**，不要自己降速再报"修好了"。
