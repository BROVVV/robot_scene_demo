## 6. 【必须先修】§13.5 闸门对「LIO 输入消失」不表态

### 6.1 现象（断电后实测，非推测）

狗断电、LIO 不再出帧之后，宿主侧的 `outputs/autonomous_search/runtime/slam_map_3d.json`
在 15 秒内的表现：

| 键 | 表现 |
|---|---|
| `generated_at` | **推进**（1789537703 → 1789537718） |
| `ros_stamp` | **冻结** 1789537461.298567（= 13:44:21，断电前最后一张地图帧）。⚠ 这一项**不能单独当死亡证据**：机器人静止时它也照样冻，见 6.3 |
| `source_map_points` | **冻结** 7908 |
| `mapping_health` | `HEALTHY` **不变** |
| `map_status` | **`LIVE`** |
| `lio_pose_valid` | **`True`** |
| `fresh` | **`True`** |

地图本体已经死了 4 分钟，前端拿到的却是**绿灯 + LIVE + fresh**。

### 6.2 根因

`LioNofixJudge` 只在**被喂 DIAG 行**时更新状态。DIAG 行不再产生 ⇒ 判据**从未被调用** ⇒
它保持最后一次表态（`HEALTHY`）**永远不变**。

`fresh` 由 `generated_at` 驱动（这正是 §13.5 的设计：让"故意冻结"与"写端死了"不塌成同一个显示），
所以 `fresh=True` 只证明**写端活着**，不证明**LIO 有数据**。

**这是我刚接的那层可观测性的盲区，不是既有 bug**：审计报告原本抱怨的是"判据从不表态所以恒真"，
现在变成了"判据停止被喂食所以保持最后一次表态"，症状同类（假绿），触发条件不同。

### 6.3 最小修法（建议，**本次未实施**）

先纠正一个**我第一版写错、已改成现在这样**的点：把"判据饿死"映射成"判据不表态"
（`health` 返回 `None`）**是没用的**，因为那条路是**放行**的：

- writer 的 `if health is not None:`（`webui_map_snapshot_writer.py:524`）会把
  `mapping_health` / `lio_pose_valid` / `map_status` **三个键整块跳过**；
- 前端于是走兜底 `slam_map_3d.js:260` 的
  `snapshot.map_status || (snapshot.fresh ? "LIVE" : "STALE")`，
  而 `fresh` 只看 `generated_at`（写端心跳）→ **结果还是 `LIVE`**。

`SUSPECT` 也接不住：它只在"判据判了 DEGRADED **且** 没有 last-good 可退"时才产出
（`:531-534`），不是给"判据不表态"准备的。

**饿死必须映射到一个会转黄、会拦的态。** 建议落点 `DEGRADED_LIO_DRIFT`：

| 条件 | `mapping_health` | `map_status` | `lio_pose_valid` | 前端灯 | 就绪闸门 |
|---|---|---|---|---|---|
| 距上次成功 `feed()` > N 秒 | `DEGRADED_LIO_DRIFT` | `FROZEN_LAST_GOOD`（有 last-good 时） | `False` | 黄 | **拦** |

三点理由：

1. **改动面最小，且只落一处。** 饥饿计时加在 `app/spatial/lio_nofix_judge.py`
   （它已经是纯逻辑、不 import rclpy，判据只要在 `health` 里多看一个时间戳）；
   下游三态分支（`frozen` → `FROZEN_LAST_GOOD`、`!= HEALTHY` → 黄）
   **已经存在，`webui_map_snapshot_writer.py` 一行都不用改**。
   `app/spatial/lio_nofix_judge.py` 在 §10.2 保护清单之外。
2. **语义上站得住，但 `health_reason` 必须写清是哪一种。** 这里的 `DEGRADED_LIO_DRIFT`
   含义是"建图数据源已不可信"，**不是**"检测到发散"。不说清的话，下一个读日志的人
   会去查一次根本不存在的 LIO 发散。
3. **必须与"从没跑过"分开。** 现在的第三态（键不写）是有意为之，原话在
   `webui_map_snapshot_writer.py:385`：「文件打不开（路径不对 / LIO 没起）时直接返回…
   这是有意为之的第三态」。**饿死是"它跑过、然后停了"，与"没起"是两件事**，
   不能塌成同一个显示。

⚠ **代价要说清，这是需要你拍板的地方：** latch 的唯一复位路径是**日志截断**（= LIO 换会话）。
所以**一次持续 N 秒的雷达短暂掉线也会把闸门锁死**，必须重启 SLAM 栈才能清。
这是真代价，也正是我把 N 取偏大的理由——DIAG 是 10 Hz，§21 静止时 60 秒来了 604 帧，
即使 N 取 15~30 s 仍有约 100 倍余量。**N 取多少、要不要另给一个"现场手动清"的出口，请你定。**

判据的接口现在是 `feed(line)` / `note_session_restart()` / `health` / `reason`
（`app/spatial/lio_nofix_judge.py:66-117`）——`feed()` 拿不到时间，所以饥饿计时需要
一个时间源；建议给构造函数一个可注入的 clock（默认 `time.monotonic`），
这样校准测试仍可确定性地喂假时间，不破坏"测试环境没有 rclpy 也能跑"这条分层。

⚠ 另一个必须一起想清楚的点：**`ros_stamp` 看起来像现成的饥饿信号，但它不是，而且它没坏。**

`ros_stamp` 是地图点云的 `header.stamp`，且**只在一帧真的换了才更新**
（`webui_map_snapshot_writer.py:287-291` 的 `if stamp != self._last_ros_stamp`），
设计意图逐字写在 `app/manual_web_demo/slam_map_snapshot.py:65-69`：「**ros_stamp 跟着数据走**，
重启也不会变」——它是给 `map_age_seconds` 用的、语义正确的字段。

它当不了饥饿判据的理由是**同形**，不是它坏了：§21 那 60 秒机器人静止、LIO 健康、
DIAG 照来 604 帧，`ros_stamp` 却冻在 `1789459374` = **LIO 启动 +5 秒**（节点 16:02:49 起，
戳是 16:02:54），整整 **21.7 小时**没动，直到 13:44:21 狗被搬动才跳。
即：

> **机器人静止 ⇒ 没有新关键帧 ⇒ 地图不重发 ⇒ `ros_stamp` 冻住** ——与「LIO 死了」完全同形。

拿它当门限，会在**每一次静止**时误报，而静止正是 §22~§28 里最常见的状态。

真正干净的心跳是 **DIAG 行本身的节拍**（10 Hz）——判据已经在吃它，
所以"饥饿超时"是这里自然的最小加法，不需要引入第二个数据源。

### 6.4 影响

**在 §22 之前修不修，取决于你怎么看这件事：** §22 的通过条件（Place count、heading_coverage、
无重影）不直接依赖这个闸门。但 §22~§28 全部是"动静结合"的验收，**一旦 LIO 真的中途掉线，
现有闸门会给你绿灯**，而这正是当初把可观测层接起来的全部理由。

## 8. 环境踩坑（本次新增，省下次的时间）

1. **`ros2 topic echo` / `ros2 topic hz` 需要显式 QoS**：`/go2w/slam/odom_base`、
   `/go2w/odom/wheel`、`/go2w/slam/map_3d` 都是 **BEST_EFFORT** 发布，默认 RELIABLE 订阅
   拿到 0 条，**看起来像话题不存在**。加 `--qos-reliability best_effort`。
2. **`setup_environment.sh` 之后必须剔除 noetic**，否则 `import sensor_msgs` / `nav_msgs`
   拿到 ROS 1 的，报 `AttributeError: type object 'type' has no attribute '_TYPE_SUPPORT'`
   或 `The message type 'nav_msgs/msg/Odometry' is invalid`：
   ```bash
   export PYTHONPATH=$(echo "$PYTHONPATH" | tr ':' '\n' | grep -v /opt/ros/noetic | paste -sd:)
   ```
3. **三个 IMU 话题名字上看不出哪路是 corrected**：`/go2w/slam/imu` 才是（戳超前
   `/utlidar/imu` **830.8 s**），三路频率都是 248.5 Hz、dt 中位都是 4.48 ms。§21 判的
   "corrected stamp"只对 `/go2w/slam/imu` 成立。偏移在 60 秒内极差 0.010~0.011 s。
4. **`dsk_zero` 非零不是故障**：它是 deskew 位移恰好 `== 0.0f` 的点数
   （`lio_3d_interface.cpp:200`），不是"没拿到时间戳"。91843 帧里 592 帧非零（0.64%），
   全是孤立单帧，与 `imu_n`/`pt` 分布**无关**。别当门限用（我第一版 §21 脚本就这么错过）。
5. **转向的硬下限**：`≤2.0°` 被运动层拒（`safety_guard.hpp:93-97` → `ERROR_INVALID_GOAL`），
   `2~3°` 会走完但判 `TURN_NOT_CONFIRMED`（`app/live_robot/motion_bounds.py:209-219`）→ pattern 中断整腿。
   实际转角读 Action result 的 `actual_relative_yaw_deg`（度）；
   `step_verified` 里**只有 `yaw_delta_rad`**，没有度字段——这是最容易踩的坑。
6. **`--max-motion-steps 0` 是"不限步数"不是"不动"**
   （`exploration_config.py:38` 是 `if max_motion_steps > 0 and ...`）。
