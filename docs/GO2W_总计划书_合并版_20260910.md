## 2. 两条语义路线的关系（**必须先搞清，否则会改错文件**）

```text
项目里同时存在两条检测路线，由 run_semantic_exploration.py --detector 切换：

  --detector llm（默认）        → app/detectors/siliconflow_vision_worker.py
                                  整图 VLM，26 s/次，不返回 mask
                                  【本轮已跑通全链路，作为基线；D1/D2/D7 的来源】

  --detector grounded_sam       → app/detectors/grounded_sam_worker.py
                                  + grounded_sam_subprocess.py（代码已存在）
                                  当前问题：模型每次重载、SAM2 只返回 mask_area_ratio
                                  【新计划书要改造的对象】
```

**结论**：新计划书**不是从零开始**，而是把已存在的 grounded_sam 路线做到"模型常驻 + 真实 mask + 3D Box"。
**llm 路线不要删**（它是可用的回退与对照基线）。

**新计划书要新建的唯一新模块**：`SemanticObjectMap`（`app/mapping/semantic_object_map.py`，当前**不存在**）。

## 3. 合并后的执行顺序

> 原则：**先让对方少走路**。阶段 0/1 是"确认底座没坏"，阶段 2–5 是新计划书的改造正文。

2. 起 WebUI 确认能看到地图与语义标注；
3. **确认不使用 rko 链路**（D5 未解决，其地图是圆的；代码/配置保留在

### 阶段 1：基线复现（30 分钟，只跑不改）


记录 D1（漏检数）、D2（同一物体观测散布）作为**改造前基线**——之后 grounded_sam 的改善幅度要跟这组数比。

### 阶段 2：模型常驻 + 真实 mask（新计划书 §3–§6，收益最大）

* `grounded_sam_worker.py` 改为**进程常驻**（模型只加载一次）；
* SAM2 **返回真实 mask** 到主进程（当前只有 `mask_area_ratio`）；
* mask 传递方式走新计划书 §5 最轻量方案；`DetectedObject` 增加 mask 字段（§23 必改清单）。

**验收**：`grounded_sam` 单帧耗时与 LLM 调用次数（§28.2、§29）。

### 阶段 3：mask → depth → 3D Box（新计划书 §7–§8，治 D2/D3）

* `DepthObjectLocalizer.localize` 改用 mask 采深度（不再只用 bbox 内框）；
* mask 深度清洗 + 去 outlier；生成 camera-frame box 与 extent；
* **对象必须有可靠 3D 坐标才允许进地图**（§12）。

**验收**：§30 mask 对 depth 的有效性、§31 物体位置稳定性（应与阶段 1 基线对比）。

### 阶段 4：语义地图与去重（新计划书 §10–§11、§24）

* 新建 `SemanticObjectMap`（数据结构 §10.1、存储 §10.2、新 ID/Merge/Confirmation §24）；
* 去重规则：**同一物体多次观测要合并；相邻同类物体不许误合并**（§11.1、§33 Case A/B）；
* 位置融合用多观测结果，object_id 稳定；
* 复用 `SLAMBridge.reproject` 支持地图校正后的重投影（§13，治 D4）。

**验收**：§33 去重 Case A（一个椅子）/ Case B（两把椅子）。

### 阶段 5：3D 显示 + 职责重分配（新计划书 §14–§15）

* WebUI 三维视图画 **3D Box + Label**（当前只画点+标签）；
  注意：WebUI 只认快照文件，**务必把 box 数据写进快照**（`webui_map_snapshot_writer.py`），
  frame 必须是 `pslam_map`（否则 `slam_map_web_state` 拒收）；
* 职责重分配：GroundingDINO（开放词汇检测）/ SAM2（精细分割）/ LLM（仅在任务开始或**确实需要时**验证目标）。

**验收**：§14 显示正确；§34 大模型目标判定。

### 阶段 6：性能与回归（新计划书 §28–§35、§40）

* 性能：必须证明"真的变快"（§28.1 必须通过 / §28.2 目标）；

## 6. 坑与注意事项（本轮实测）

1. **代理会假装 GitHub 不通**：`https_proxy=socks5://127.0.0.1:17891` 对 `github.com` TLS 是坏的，
   但 `api.github.com` 正常 —— 推送要 `env -u https_proxy -u HTTPS_PROXY ... git push`（直连 200/0.98 s）；
2. **两个仓库别搞混**：控制主机 → `BROVVV/robot_scene_demo`；机器狗 → `BROVVV/robot_scene_demo-go2w-deploy`；
   **机器狗没有外网**，它的代码要经控制主机中转；
3. **重启映射栈 = 作废语义坐标**（D4）：先采语义就别重启；重启后要重采；
4. **QoS 陷阱**：RELIABLE/BEST_EFFORT 混用会**静默收不到数据**（bag 录制、WebUI web_scan 都踩过）；
5. **WebUI 只读快照**（`outputs/autonomous_search/runtime/slam_map_3d.json`）且只接受 `pslam_map` frame；
6. **外网 VLM 不可靠**（D7）：任何依赖它的流程都要有重试与降级；
7. **`run_autonomous_loop` 要求 `sport.mode == 1`**（平衡站立）；遥控模式下（mode=3）会直接拒绝；
8. **轮式 odom 只作运动学参考**，不可用于"是否回到原点"判定（D6）。

### 11.2 `semantic_goal_selection_count` 恒为 0 的根因（**推翻了 §10.7 原先的猜测**）

§10.7 原先写的是"需查 `SemanticSearchController` 的候选打分为何从不选中"。**这个方向是错的**，

```json
{"directive_id": "directive_0828e7f43b9f", "kind": "reobserve_sector",
```

真正的断点在候选生成器：`--spatial-v2` 会把 explorer 的候选生成器整个替换掉

```python
if local_executor is not None and local_executor.active:
    goal = local_executor.next_goal(...)
    if goal is not None:
        return [goal]        # 直接返回，candidate_goal_generator 的 A 分支根本不执行
```

`LocalGoalExecutor` 打的 provenance 是 `{"source": "local_goal_executor"}`，而
`autonomous_explorer.py:1070` 的白名单只有 `semantic_navigation_directive` /
`semantic_anchor` → 全部落进 `fallback_goal_selection_count`。

**语义其实一直在生效**：这些 goal 由 `SpatialSearchReasoner` 产生的
`ExplorationIntent`（`intent_type=APPROACH_TARGET`、`intent_id=intent_verify_target`、
provenance.source=`semantic_navigation_v2`、`match_state=STRONG`）驱动，goal 的
`semantic_reason` 是 `"STRONG/VERIFY target candidate requires real visual verification"`。

**结论：这是计数器口径没跟上 spatial-v2 的执行路径，不是功能缺陷。**
判断语义是否真在起作用，看 `selected_goal` 事件里 goal 的 `semantic_reason` 和

**IMU 时间戳轴在宿主机时钟阶跃后与雷达扫描时间基静默脱钩。**

因果链（每一环都有实测数字或源码行号，不是推测）：

1. 宿主机时钟被 NTP 向前阶跃 **4.673 s**。
2. `imu_timestamp_aligner` 已锁定的 offset 是 `receive − sensor = 790.621305`，
   阶跃后真实 offset 变成 `795.294101`，漂移恰好 4.673 s。
3. 旧门限 `max_offset_step_s = 5.0` **正好把这个缺口盖住** —— 既不重锁、也不报警。
4. 于是 IMU 修正戳继续停在旧时间基，而 Pandar 扫描已经走到新时间基。
5. LIO 只在**扫描自身点时间跨度内**取 IMU（`lio_3d_interface.cpp:158-173`
   的严格窗口匹配，`start_stamp = scan_stamps.front()` … `end_stamp = scan_stamps.back()`），
   两个时间基错开 4.673 s ⇒ **一帧都匹配不上**，`imu_n` 恒为 0。
6. `imu_n = 0` ⇒ 没有预积分、没有去畸变、没有运动先验 ⇒ 退化成纯 ICP。
7. 纯几何配准的位姿**照样被当成关键帧写进位姿图** ⇒ 同一面墙被几个不同角度的
   副本叠在一起，就是 WebUI 上的重影。

**这不是"IMU 断了"，是"IMU 还在流但一帧都用不上"** —— 所以单看
`/go2w/slam/imu` 的话题频率（实测 229–250 Hz，一直正常）永远发现不了。

#### 12.3.3 改了哪四处

| # | 文件 | 改动 |
|---|---|---|
| 1 | `ros2_ws/src/plain_slam_ros2/src/lio_3d_node.cpp:215` | `dt = std::clamp(stamp - prev_stamp, 0.0, 0.1);` |
| 2 | `.../scripts/imu_timestamp_aligner.py` | `max_offset_step_s` 默认 `5.0 → 0.05`；下限 `0.1 → 0.001` |
| 3 | 同上，阶跃分支 | 由 `_require_restart()`（判死）改为**重新锁定**：`_locked_offset = None`，清 `_last_corrected_sec`，用当前样本重开启动窗口 |
| 4 | 同上，数据空洞分支 | 重锁窗口内（`_locked_offset is None`）遇 gap 时清空 `_startup_offsets` 重攒，**不再判死** |

配套：`imu_fallback_adapter.py --max-offset-step-s` 默认 `0.2 → 0.05`，
`plain_slam_go2w.launch.py` 里的实参 `0.2 → 0.05`（launch 传的是实参，改默认值不生效）。

**Hole 1 为什么必须修**：`dt` 取自相邻两条**已收到**的报文
（`lio_3d_node.cpp:215`），全链路**没有任何钳位**（唯一的 `dt` 比较是
`lio_3d_interface.cpp:302` 的 `if (dt > 1.0)` 关键帧节流）。重锁窗口停发
2.015 s，重锁后第一帧的 `dt = 6.689 s`，直接进
`imu_preintegrator.cpp:164` 的 `t += v_prev * dt`。按实测 `v` p50 0.454 m/s，
一次先验就偏 **3 m**，而 `max_correspondence_dist` 只有 **0.5 m** ——
`lio_3d_interface` 在优化不收敛时**依然保留该位姿**，于是又一帧错位墙进地图。
正常相邻间隔 max 8.994 ms，0.1 s 上限有 11 倍余量。

**Hole 2 为什么门限必须小于 0.075 s**：门限一旦大过消费端容忍度，落在
`(0.075, 门限]` 的阶跃既不重锁、又让 IMU 戳整体滑出扫描窗口 ——
`imu_n` 恒为 0，与 09-11 事故**同型同签名**。已回放验证：0.15 s 阶跃
（ntpd 默认 step 阈值就是 128 ms）在旧门限 0.2 下被静默吞掉，在新门限 0.05 下正确重锁。

**Hole 3 为什么重锁窗口内不能判死**：重锁会维持 `_locked_offset = None`
达 `lock_after_samples` 个样本（248 Hz 下 2.0 s），而**全仓没有任何生产代码调用
`reset()`**。判死等于建图中途任意一次 2 s 链路闪断都能永久废掉整轮建图。

### 12.5 `mapping_health` 等字段为 null 的排查结论（**非回归，是手动模式既有现象**）

#### 12.5.1 现象

手动模式（`start_manual_web_demo.sh`）下 `/api/slam/map3d` 返回：

```
mapping_health: null, health_reason: null, map_revision: null,
mapping_session_id: null, rejected_counts: null, lio_pose_valid: null
```

（而 `point_count` / `fresh` / `map_age_seconds` / `voxel_size_m` 都正常。）

#### 12.5.2 根因：**两个 WebUI 入口各自起自己的快照 writer，写的是同一份字段集合，但集合不同**

| 入口 | 启动的 writer | 写 health/session/revision 吗 |
|---|---|---|
| `start_autonomous_search_web.sh:376` | `plain_slam_web_bridge.py`（走 `SlamWebMapState`） | **写**（`slam_web_map_state.py:274-295`） |
| `start_manual_web_demo.sh:156` | `webui_map_snapshot_writer.py` | **不写** |

读取端 `slam_map_snapshot.py:55` 是 `result = dict(value)` **原样透传**，
不补默认值（`unavailable_snapshot()` 里那套 `"UNAVAILABLE"` 默认值**只在文件缺失时**生效）。
所以手动模式下这几个键本来就取不到 → `null`。

**当前机器上 `plain_slam_web_bridge.py` 根本没在跑**（`runtime/slam_web_bridge.pid`
还是 2026-09-01 的），`ps` 里只有 `webui_map_snapshot_writer.py`。
旧快照文件里曾经存在的那些 health 值，是**当年跑自主搜索时桥接节点留下的残留**。

#### 12.5.3 影响（两处，第 2 条是实打实的）

1. **`reset_plain_slam_session.sh` 的 [6/6] 步永远等不到 HEALTHY**
   （`read_field mapping_health` 恒为空），每次重启白等满 60 秒循环再继续。
   不阻塞流程，只是慢。
2. **`web_server.py:377` 的 `slam_map_not_drifting` 门在手动模式下恒真**：
   `slam.get("mapping_health") != "DEGRADED_LIO_DRIFT"` → `None != "…"` → `True`。
   该键在 `blocking` 组（384-388 行）。

**这条门不是摆设**：注释（375-376 行）写明它是 §10.2 的"LIO 造假平移、地图已冻结时
不许开自主搜索"。而 `app/manual_web_demo/search_routes.py:110-127` 正是这条门唯一的
执行点（命中则 409），**manual web demo 确实能开自主搜索** ——
本轮 `trash_search7` 走的就是这条路径。所以恒真 = **用户真实工作流里这层防护是失效的**。

> 本轮改动之前它同样恒真（旧文件里的陈旧值恰好也非 DEGRADED），**不是本轮引入的**，
> 但确实一直没有防护。

#### 12.5.4 为什么不顺手修：**上游没有等价信号，补它就得复制一份语义**

直觉上"订阅 `/go2w/slam/health` 透传一下就行"，但查证后**不成立**：

* `/go2w/slam/health`（`diagnostic_msgs/DiagnosticArray`）由 **C++ 节点
  `plain_slam_health_monitor` 独立发布**（`plain_slam_go2w.launch.py:136`），
  与桥接节点无关，手动模式下**一直在跑**（实测 `Publisher count: 1`）。
  它给的 flags 是（`plain_slam_health_monitor.cpp:225-253`）：
  `TIMESTAMP_SYNTHETIC` / `POINTCLOUD_SCHEMA_ERROR` / `GROUND_ESTIMATE_FALLBACK` /
  `IMU_DEGRADED` / `IMU_SYNTHETIC` / `LIO_STALE` / `MAP2D_STALE` / `EXTRINSIC_CANDIDATE`。
* 但门要判的 **`DEGRADED_LIO_DRIFT` 不在这套 flags 里** ——
  它是 `SlamWebMapState` **自己算的**（`slam_web_map_state.py:211`），
  依据是**地图接受率/拒绝计数**（`accepted_maps` / `rejected_counts`），
  也就是"位姿在动但地图不再长"，与 health monitor 那套"话题是否新鲜"是**两个语义**。

所以要让门恢复作用，只有两条路，都不划算：

* 把桥接节点的漂移判定逻辑复制进 `webui_map_snapshot_writer.py` ——
  同一份语义两处维护，正是要避免的；
* 或者同时启动 `plain_slam_web_bridge.py` —— **两个 writer 抢同一个文件**
  （都走 `os.replace` 覆盖），5 秒周期互相抹掉对方字段，比现在还糟。

且门要防的那个成因（IMU 时间轴脱钩 → 假平移 → 地图冻结）**已在 §12.3 修复消除**，
边际收益进一步变小。

**结论：记为已知项，不动。** 若要恢复这层防护，属于独立改动，应单独立项
（建议做法：让 manual writer 订阅 health 并把 `LIO_STALE`/`IMU_DEGRADED` 映射为
非 HEALTHY 值，**不动** `DEGRADED_LIO_DRIFT` 的语义）。

#### 12.5.5 补偿手段（漂移检测能力并没有丢）

漂移的真实信息**一直在 ROS 话题上**，只是没进 WebUI 快照：

* `/go2w/slam/health`（`diagnostic_msgs/msg/DiagnosticArray`）由 plain_slam 上游发布；
* 更本质的哨兵是 `runtime/go2w/sessions/plain_slam_go2w.launch.log` 里的 `imu_n`
  —— 见 §12.3，**`imu_n=0` 就是地图重影的成因本身**。

本轮验收期间就是靠直接 grep 这个日志完成的退化监视（§12.6）：
判据是 `imu_n=0` / `dsk_zero≥1000` / `act<0.7` / 时钟重锁。
**不要**拿 `dsk_max` 的绝对值当退化判据 —— 运动时 `dsk_max` 大恰恰是
去畸变**在工作**（w=1.37 rad/s 时一帧转 7.8°，5 m 处即 68 cm 位移，
与实测 `dsk_max=0.81` 吻合）；真退化时 `dsk` 反而趋近 **0**（没有 IMU 就没法去畸变），
看着"很干净"，位姿却全靠纯 ICP —— 这正是 §12.3 里最难察觉的地方。

## 13. 交接书增补（2026-09-11 WebUI「地图发糊」轮）

### 13.1 现象

用户在 WebUI 上两次反馈同一条：截图里地图"比较糊"，并自己给出了假设 ——
**"感觉像是把很多次建的图重叠在了一块，但是图和图之间没有完全把角度对齐"**。
第一次（§12.3）我按"数据里真有重影"去查，修了 IMU 时间轴（真问题，见 §12.3）。
第二次用户说"还是有略微的重影"，**这次查出来的结论不一样**。

### 13.2 排查方法：不看代码猜，先把用户实际看到的画面复刻出来

`app/manual_web_demo/static/slam_map_3d.js` 的渲染管线很短，可以直接照抄成
Python（`/tmp/render_webui.py`，思路可复用）：

```
pitch=0.63, yaw=-0.72                     // 默认视角
span  = max(2, dx, dy, dz*1.8)            // 画幅（米）
scale = min(W,H)*0.78/span                // px/m
size  = max(1.1, min(3.2, W/720))         // 每个点画成 size×size 像素
rx = cos(yaw)*dx - sin(yaw)*dy
ry = sin(yaw)*dx + cos(yaw)*dy
screen_x = W*0.5 + rx*scale
screen_y = H*0.54 - (cos(pitch)*dz - sin(pitch)*ry)*scale
depth    = sin(pitch)*dz + cos(pitch)*ry   // 只用来分 6 个 alpha 桶
```

照抄之后一眼就看出问题，不用再猜。

### 13.3 结论：**数据里没有重影，糊是渲染出来的**

两条独立证据：

1. **按"到轨迹的距离"分层渲染**（`/tmp/layer_check.py`）：
   * `0–5 m` 层：一张**轮廓清晰的矩形房间**，墙是单线条，内部家具可辨；
     没有任何错位叠加。
   * `5–12 m` 层：**空间上与房间完全分离**的走廊结构（矩形边界、栏杆条纹）。
   * 幽灵点的特征应是"整帧点云被甩出去"→ 会形成与房间同尺寸、**彼此重叠或
     角度错开**的矩形块。实测不是这个形态。
2. **距离分布各向异性**：按方位角分 8 个 45° 扇区，p95 距离从 1.56 m 到 9.42 m
   不等。若是球状弥散的幽灵点，各扇区应当接近。

### 13.4 真因（两条，都在渲染层）

1. **默认视角是 36° 斜视（`pitch=0.63`），不是俯视。**
   投影式 `vertical = cos(pitch)*dz − sin(pitch)*ry` 里 `sin(0.63)=0.59`：
   远处**低**点（大 `ry`）与近处**高**点在屏幕上落进同一片区域。用户看到的
   "几张图叠在一起、角度没对齐"就是这个几何混叠 —— 他的直觉方向是对的，
   只是"多次建图"其实是"不同距离的结构"。
2. **画幅由点云 bbox 决定（`centerAndSpan()`），而地图含 12 m 内的走廊。**
   bbox 有 27×31 m，房间（8 m）只占画幅 26%，剩下的全被走廊占掉。

### 13.5 改了两处（都是显示层，不碰 SLAM 数据）

| 位置 | 改动 |
| --- | --- |
| `app/manual_web_demo/static/slam_map_3d.js:22` | `pitch` 默认 `0.63 → 1.35`（36°→77°，近俯视） |
| `app/manual_web_demo/static/slam_map_3d.js:43` | `centerAndSpan()` 优先用 `focusBounds`，无则退回 `bounds` |
| `app/manual_web_demo/static/slam_map_3d.js` `applySnapshot` | 读 `snapshot.focus_bounds` |
| `scripts/go2w/webui_map_snapshot_writer.py` | 新增参数 `focus_margin_m`（默认 3.0）+ `_focus_bounds()`，快照多一个 `focus_bounds` 字段 |

`focus_bounds` = **轨迹 bbox + `focus_margin_m`**（z 用 `[min_z_m, max_z_m]`）。
轨迹不足 20 点、或 `focus_margin_m=0` 时给 `null`，前端自动退回点云 bbox。
读取端 `load_slam_map_snapshot()` 是 `dict(value)` 全量拷贝，字段自然透传
（已 curl `/api/slam/map3d` 确认）。

### 13.6 关键实测数字（2026-09-11，用户遥控走完房间后的那次建图）

| 项 | 值 |
| --- | --- |
| 点云 span / 房间占比 | 30.9 m / **26%** → `focus_bounds` 后 13.8 m / **58%** |
| 修复前（原始地图 + 旧视角） | span 93.6 m，房间占 **9%** |
| 点渲染尺寸 vs 体素 | `size=1.94 px`，而 `scale=19.2 px/m` → 1 个点 = **10.1 cm** 地面距离，**大于** 5 cm 体素（点会互相盖住） |
| 轨迹过滤实际效果 | 只砍掉 **1%**（>12 m 的 10–12 m 尾巴）；p99=9.98 m 与单帧扫描最远 9.9 m 吻合 |
| 分层点数 | 0–5 m: 47614；5–12 m: 14345 |

### 13.7 数据层同时做的两处（作用比原先以为的小，但保留）

1. `min_z_m` 默认 `-0.45 → 0.15`。地面在雷达系 z≈−0.23，且实测是
   −0.336 / −0.097 两张相距 0.24 m 的平行面（拟合倾角仅 0.08°，**不是整体倾斜**）。
   俯视投影时地面回波把房间填成一整团（z<0 占 30%），不提结构信息。
   点数 103043 → 61959。启动脚本入口 `GO2W_WEBUI_SNAPSHOT_MIN_Z_M`。
2. `trajectory_radius_m=12.0` 轨迹过滤 + 50% 丢弃护栏（详见参数处注释）。
   **保留**：它挡的是真实的误回环离群帧，只是量没当初以为的大。

### 13.8 本轮被推翻的旧结论

* **"12 m 外的点占了 3.9%、把画幅撑到 60 m、这才是发糊"** —— 量对，
  但归因错：那些点是**真实走廊**，且砍掉后房间仍只占 26%。真因是 §13.4。
* **"地面回波是发糊主因"** —— 修掉后画面确实干净一档，但它不是
  "几张图叠在一起"那种观感的来源。

### 13.9 怎么验证 / 怎么回退

* 验证：`curl -s localhost:8765/api/slam/map3d | python3 -c "import sys,json;
  print(json.load(sys.stdin)['focus_bounds'])"` 应给出非 null 的框；
  浏览器 **硬刷新**（静态文件是 `no-store`，普通刷新即可）后地图应占满画幅。
* 回退视角：把 `slam_map_3d.js` 的 `pitch` 改回 `0.63`。
* 回退聚焦：`-p focus_margin_m:=0`（或把 `focus_bounds` 置 null）。
* 重新渲染对照图：`/tmp/render_webui.py`、`/tmp/layer_check.py`、
  `/tmp/final_compare.py`（都在本次会话里现写的，逻辑已在上面 13.2 给出）。

### 13.10 给下一个执行者的提醒

* **不要用 `pkill -f` 重启 writer**：bash 工具自身的命令行里含
  `webui_map_snapshot_writer.py` 字面量，`pkill -f`/`ps|grep` 会把**调用它的
  shell 自己**匹配进去并杀掉（退出码 **144**，本会话踩了两次）。
  安全做法：`PAT='webui_map_''snapshot_writer'` 字符拼接后再匹配，
  且**查杀与启动分成两条命令**。
* 判断"地图糊不糊"**必须先把 WebUI 的画面复刻出来**（13.2），
  直接看数值(`p95` 厚度、点数)会得出错误结论 —— 本轮就是这么绕了一圈。
