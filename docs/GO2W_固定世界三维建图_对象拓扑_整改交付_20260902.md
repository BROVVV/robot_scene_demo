```

`/utlidar/imu` 的传感器时钟比 ROS 时钟落后 **730.94 s**，远超 `passthrough_tolerance_s=5.0`，
必须走 `raw + offset`。而 `ImuTimestampAligner` 在启动窗口（`lock_after_samples=500`）**未锁定前**
就用 `statistics.median(self._startup_offsets)` 这个**滚动**中位数生成 `corrected`：每来一个样本中位数
就动一次，`/utlidar/imu` 实测 315 Hz（raw 每次只增 ~3.2 ms），中位数一次下沉就让
`corrected <= _last_corrected_sec` 成立 → `_require_restart()` → `_restart_required` 永久闭锁。
第 8 个样本就死，**重启 session 必然复现**，交接书"重启 session 就能恢复"的假设在这台机器上不成立。
这条滚动中位数本身就违反 §8.4 自己的要求（不许根据 callback 抖动拖动时间轴）。

修复（两处，均为最小改动）：

- `ros2_ws/src/go2w_plain_slam_bridge/scripts/imu_timestamp_aligner.py`：需要偏移且尚未锁定时
  **只收集样本、不输出**（返回 `OFFSET_ESTIMATING_SENSOR_STAMP`，`valid=false`、`restart_required=false`）；
  锁定后 `corrected = raw + 常量偏移`，天然单调，回退检查永不误触发。
- `ros2_ws/src/go2w_plain_slam_bridge/scripts/imu_fallback_adapter.py`：真实 IMU 流新鲜（<1 s）时
  **一律不发** `SYNTHETIC_STATIC`。旧条件带 `and state["valid_real"]`，会在估计期/闭锁期给 LIO 灌
  `az=9.81` 的假静态 IMU，把真实故障盖住。

回归测试：`tests/test_imu_timestamp_aligner.py::test_startup_jitter_never_locks_out_the_imu_stream`
按真机参数（offset≈730.942 s、raw 步长 4.5 ms、中位数下沉 50 ms）复现闭锁；
`test_large_constant_offset_is_locked_after_the_startup_window` 改为断言"锁定前一个样本都不喂 LIO"。

### 15.13 §12.2 根因：`/utlidar/imu` 的 yaw 角速度符号与机身相反（已修）

先修掉挡住运行时诊断的工具故障：`ros2 topic echo` 对任何标准消息都报
`The message type '...' is invalid`，根因是 **`ros2_ws/install/setup.bash` overlay 遮蔽了标准
消息的 Python typesupport**。只 source `/opt/ros/humble/setup.bash` + DDS 三个环境变量
（`/tmp/rosenv.sh`）即完全正常。诊断探针一律用这个环境，运动仍用
`scripts/go2w/setup_environment.sh`，两个进程互不干扰。

探针 `/tmp/gyro_probe.py` 同时记录原始陀螺积分、LIO IMU 预积分姿态、`odom_base`、轮式
odom。双向实验 `/tmp/diag_signs.sh`（左 +30° 再右 -30°，`/tmp/diag_signs.csv`）：

```
左转  wheel yaw -51.98 -> -22.73  = +29.25°   （action result +29.278）
      gyro-z 积分  -0.03 -> -28.54 = -28.51°
      LIO imu yaw -15.18 -> -6.72  = +8.46°（方向对，幅值 29%）
      LIO xy (-3.524,+0.198) -> (+0.012,+4.728)   假平移 5.75 m

右转  wheel yaw -22.73 -> -50.93  = -28.20°   （action result -28.193）
      gyro-z 积分 -28.54 -> -1.16  = +27.38°
      LIO imu yaw  -6.72 -> -10.19 = -3.47°
      LIO xy (+0.012,+4.728) -> (-0.505,+3.992)   位移 0.90 m

三条互相独立的证据：

1. **符号**：陀螺 z 与轮式 / action result 每次都反号，幅值差 <3%（28.51 vs 29.25；
   27.38 vs 28.20）。左右转都成立，不是偶发。
2. **加速度未反号**：静止重力 `(+2.76, -0.03, +9.88)`，z 轴朝上，倾角
   `atan2(2.76, 9.88) = 15.6°`，与 `generated_lio_3d_params.yaml` 的 `imu_to_lidar`
   旋转矩阵解出的 pitch 15.7° 吻合 —— **外参链是对的**，之前对 16° pitch 的怀疑排除。
3. **三轴投影**：已知 pitch 15.7°，base 转 +29.25° 的理论陀螺投影是
   `(+7.92, 0, +28.15)`；实测 `(+7.9, -5.1, -28.5)`。只有 z 需要翻转即两轴精确吻合
   （y 的 -5.1 是四足转向中的身体侧摆）。故修正量是 `gyro_sign = (1, 1, -1)`，
   不是整体取反、也不是 `Rx(180)`。

因果链：LIO 拿到反向 yaw 角速度 → 预积分姿态往反方向走 → 点云配准必须对抗约 2 倍的
旋转误差 → 残余旋转被吸收成平移，于是原地转向产出 1.2–5.8 m 假平移。系统的
`lio_drift_frozen` 保护判断正确（地图冻结、health 不虚假恢复），拦住的是这个根因的后果。

（"the raw lidar gyro z is opposite"，操作员目视确认 `+10°` 指令是物理左转）。当时因为
`use_imu_as_input=false`（lidar-only，IMU 不进姿态）而选择不改陀螺、在输出侧
`yaw_reflect=true`。现在 plain_slam 是 IMU 进姿态的松耦合 LIO，必须在输入侧修正。
plain_slam 链路上没有任何 yaw 反射（已 grep 确认），不存在双重修正。

### 15.16 §12.3 第一次跑暴露的第二个真实缺陷：合成静止 IMU 回退的重力向量（已修）

3. **15:03:08** `slam_3d_node` `exit code -6`：`1 edges were detected.` →

**残差为什么反号衰减而不是单调收敛。** `dyaw` 的算式在
`app/navigation/topology_route_executor.py`：

```python
bearing = frontier.bearing_deg if frontier is not None else current_yaw_deg
delta = (bearing - current_yaw_deg + 180.0) % 360.0 - 180.0
```

`frontier.bearing_deg` 来自 BEV 每帧重算（`frame: "lightweight_depth_bev"`，
frontier id 里带坐标 hash，与 place_graph 的 `frontier:P1:xx` 是两套），所以
**目标角本身跟着机器狗的朝向走**：转过去之后视野变了，最开阔的方向重算到另一侧，
残差就反号。实测幅度序列 20.32 → 16.11 → 14.55 → 12.30 → 12.16 → 7.85 → 7.00
→ 8.27 → 8.15，衰减比约 0.8，符号严格交替。算式吻合校验（cycle 6）：frontier
`bearing_deg=26.87`，pose `yaw=0.8236 rad = 47.19°`，26.87 − 47.19 = −20.32，
与决策记录里的 `relative_dyaw=-20.321170334208773` 精确一致。

旧代码的对准窗是硬编码 `abs(delta) > 5.0`，比这条衰减曲线在 7~8° 的平台还小，
所以必须等衰减穿过整个平台才闭合 —— 这就是 11 个 cycle 的来源。修复只放宽
same-place frontier 这一支的窗口：

```python
    max_turn_deg: float = 30.0
    forward_step_m: float = 0.3
    # Frontier bearings are recomputed from every BEV frame, so the target angle
    # moves with the robot's own heading and the residual flips sign every cycle
    # while decaying by ~0.8.  Measured search_20260902_172911: cycle 4 starts at
    # -30 deg and the residual only drops under 5 deg on cycle 15, so 11 of a
    # 20-step budget go to pure head-swinging before the first advance.  A 15 deg
    # window closes on cycle 8 (-14.6 deg) instead, and one 0.3 m step at 15 deg
    # is off by under 0.08 m laterally.
    frontier_align_deg: float = 15.0
```

```python
                if abs(delta) > self.frontier_align_deg:   # 原为 abs(delta) > 5.0
```

15° 这个数是从上表反推的：残差第一次落进 15° 是 cycle 8（−14.55°），比 cycle 15
早 7 个 cycle；而 0.3 m 步长在 15° 偏差下的横向误差是
`0.3 × sin 15° = 0.078 m`，小于一个体素格（0.12 m），不会把点云铺歪。

**`topology_route_executor.py:208` 的跨 place 分支不动。** 那一支的
`abs(delta) > 5.0` 保留原值，理由是数据源不同：它的目标角是
`math.degrees(target_place.pose.yaw)`，即 PlaceGraph 里持久化的 Place 位姿，
机器狗转向不会改变它，残差单调收敛而不反号。更直接的依据是上表最后一列 ——
20 个 cycle 的 `route.place_path` 全是 `['P1']`，**跨 place 分支一次都没进过**，
没有任何实测数据支持去改它。按「禁止过度设计」，不改。

#### §15.21 六 `TARGET_FOUND` 复核：不是伪报，但确认落在了错误的对象上

`search_20260902_180313_f3ab3bc5` 在 cycle 8 以 `TARGET_FOUND` 结束。归档里最先
看到的是一个刺眼的矛盾：`target_found.object_id` 是 `obj_005`「**纸箱**」，而
搜索目标是「白色垃圾桶」。第一反应（本会话一度得出的结论）是"现场没有白色垃圾桶，
这是伪报"。**这个判断是错的，已自我修正。** 定论如下。

**1）目标真实存在 —— 以图像为准。** 触发确认的那一帧是 `bundle_343131`
（`/tmp/bundle_343131.jpg`）。图中确有一个白色塑料网格垃圾桶，位于画面中央偏
左下、玻璃门内侧、白色矮柜左侧。Full VLM 的复核语与图像逐项吻合：

> 图2中是白色带网格的垃圾桶，符合目标描述；图1中其位于玻璃门旁，满足"旁边"关系

verifier 结果 `confirmed = true`、`attempts = 1`。timeline 也是干净的：
`TARGET_CONFIRMED`(1788344175.415) → `SEARCH_FINISHED`(1788344175.741)，间隔
0.326 s，`_backend.stop()` 已调用。**§12.6 的「找到目标后停稳、复核并结束」在
事实层面是满足的。**

**2）缺陷 (a)：确认标记打到了一个无关对象上（已修）。** 旧的 `_target_object_id`
拿"当前帧的标签集合"去撞 object_map，返回**插入顺序里第一个命中的对象**：

```python
labels = {item.get("label_zh") or item.get("label") or ... for item in observation.scene_objects}
for object_id, entry in self.semantic_graph.object_map.objects.items():
    if entry.label in labels:
        return object_id          # ← 插入顺序第一个，与"目标"无关
```

那一帧的标签集合是 `{玻璃门, 办公桌, 纸箱, 黑色背包, 红色灭火器}`，object_map 的
前 5 个对象是 `办公椅 / 机器狗 / 文件柜 / 玻璃隔断 / 纸箱` —— 于是"纸箱"命中，
`obj_005` 被盖上 `target_confirmed`。这个 `obj_005` 的实际状态是
**STALE、距离 4.17 m、last_seen 比确认时刻早 770 s**，与被确认的垃圾桶毫无关系。

修法是按搜索目标本身取对象，不再看当前帧命中了什么
（[app/live_robot/autonomous_explorer.py:1152](app/live_robot/autonomous_explorer.py#L1152)）：
先按 label 与 `self.target` 相等取，取不到再按双向子串包含取。加包含是因为场景
VLM 对同一个桶的措辞每帧都在变——历史 `search_worker.log` 里同一现场先后写成
「蓝色和浅绿色的垃圾桶」「蓝色塑料筐和浅绿色塑料筐」「蓝色和绿色的垃圾桶」——
纯相等匹配会让确认永远停在 Place 层。包含仍然拒绝无关对象：「白色垃圾桶」既不
包含也不被包含于「绿色垃圾桶」或「纸箱」。

**3）缺陷 (b)：那一帧的场景理解漏掉了目标本身（上游 VLM 行为，未修，如实记录）。**
`bundle_343131` 的 `scene_objects` 只列了 5 个物体：玻璃门 0.98、办公桌 0.92、
纸箱 0.91、黑色背包 0.93、红色灭火器 0.89 —— 画面中央那个白色网格垃圾桶不在其中。
scene_objects 是 object_map 的唯一入口（depth localizer → object_map），所以
**object_map 的 35 个对象里根本没有这个白色垃圾桶**：唯一带"垃圾/白/绿"字样的是
`obj_024`「绿色垃圾桶」（TENTATIVE，obs=2），那是现场另一个桶。

这是场景理解与目标复核两条链的不一致：目标复核走 Quick VLM 的 `target_objects`
（契约里 `objects` 只装真正的目标候选，`target_decision` 是 gate），score 最高的
框送 Full VLM 复核 —— 这条链**判对了**；场景理解走另一次全景调用，**漏检了**。
修复 (a) 之后，遇到这种情况 `_target_object_id()` 返回 `None`，确认只落在 Place
层（`place.target_confirmed = True`），不再去污染一个无关对象。这是正确的降级：
宁可拓扑里没有高亮对象，也不能把"找到了"盖在纸箱上。

**4）缺陷 (c)：确认标记比 WebUI 快照晚一步落地（已修）。** 整个确认路径只 emit
一次带 `semantic_navigation_graph` 的 `memory_update`，而 `mark_target_confirmed`
原先排在这次 emit **之后**。后果是 `webui_state.json` 里 35 个对象、
`object_topology` 35 节点 227 边的 `is_target_confirmed` **全部为 false**，而同一
会话的 `place_graph.json` 里确实有 1 个 `target_confirmed` 的 Place —— 标记确实
写进了内存，只是永远没进过任何一份发给前端的快照。修法是把两行 mark 移到
`self.semantic_graph.to_dict()` 之前
（[app/live_robot/autonomous_explorer.py:558](app/live_robot/autonomous_explorer.py#L558)）。

**5）取证时踩到的两个陷阱（记录下来，避免下次重复）。**

- 归档 `semantic_map.json` **不能**用来判 `semantic_graph` 的状态。
  `search_executor.py:536` / `autonomous_explorer.py:1360` 写进去的是
  `explorer.semantic_graph.to_dict()`（含 `nodes`/`edges`/`places`/`objects`/
  `frontiers`/`object_topology`），但 `run_semantic_exploration.py:2670-2674` 在
  会话末尾又用 **worker 层另一个** `SemanticObjectMap.to_dict()`（只有
  `{objects, merge_distance_m}`）覆盖了同名文件。按 `nodes` 取键只会得到空。
- 一次会话里并存**两套编号不同的 object_map**：`explorer.semantic_graph.object_map`
  有 35 个对象、绿色垃圾桶是 `obj_024`；worker 层那套有 28 个、`obj_024` 是
  「黑色包」。判 semantic_graph 一律读 `webui_state.json` 的
  **`spatial.semantic_graph`**（不是 `spatial.semantic_navigation_graph`，
  那个键不存在）。
