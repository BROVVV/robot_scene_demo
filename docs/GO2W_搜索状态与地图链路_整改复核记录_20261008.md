## 1. 修掉的两个真因（同一类缺陷，症状互不相似）

> 本轮一共修了 **4 处**。另外两处不在本节：执行模式的 through_poses BT（§4.1.1）、

### 1.1 TF 位姿查询：`timeout` 传了 float，且按 `now()` 查

`app/navigation/nav2_search_backend.py` 的 `_pose_provider` 原写法：

```python
tf_buffer.lookup_transform(MAP_FRAME, base_frame,
                           node.get_clock().now(), timeout=tf_lookup_timeout_s)
```

两个 tf2 语义坑叠在一起，被同一句 `except Exception` 吞成「TF 没到」：

| 坑 | 实测 |
| --- | --- |
| `timeout` 是 float（默认 `0.2`），tf2 签名是 `timeout=Duration()` | 在 `timeout != Duration()` 比较处抛 `TypeError: ("Can't compare duration with object of type: ", <class 'float'>)` |
| 按 `now()` 查 | TF 从发布到进 buffer 有几十毫秒延迟，实测差 **0.037 s**（请求 `1791439845.3167`，最新数据 `1791439845.2796`）⇒ `ExtrapolationException` |

后果链：`get_pose()` 恒 `None` → `AutonomousExplorer` 拿它**覆盖** `observation.pose`
（`app/live_robot/autonomous_explorer.py:644`）→ `_has_xy` 为假 → `robot_pose=None` →
地图系后端表达不出 §6.7 的 `NAVIGATE_POSE` → 候选只剩一句 `local_executor_no_primitive`。

**而 `health()` 的 `pose_quality` 取自 readiness、照报 `metric`**：就绪四项全绿，位姿其实一直是空的。
这是本条最贵的地方——闸门看不见它。

改为 `rclpy.time.Time()` + `Duration(seconds=...)`，与仓库另一处 TF 调用
（`app/spatial/rtabmap_spatial_provider.py:222`）逐字一致。真机确认：

```
RobotPose(x=-0.288, y=0.018, frame_id='map', quality=METRIC, source='tf:map->base_link')
```

### 1.2 `_wait_result` 的阻塞等待里没人 spin

1.1 修好后，第 6 次会话不再 56~60 s 暴死，但每个候选变成 `"compute path timeout"` /
`reject_reason: NO_PATH` / `path_length_m: 0.0`。

真因在 `app/live_robot/autonomous_explorer.py` 的 `_wait_result`：它用裸 `time.sleep(0.2)`
轮询 `get_navigation_status`，而 `RosActionClientPort.poll()` 的文档自己写着
「必须有人持续 spin 这个 node，否则状态永远停在 UNKNOWN」——`run()` 是阻塞调用，
这个等待窗口里没有任何人在 spin ⇒ `ComputePathToPose` 的回执永远读不到，
`plan_timeout_s=10.0` 到点就判规划超时。

改法与 bootstrap 完全一致：复用已有的 `_pump_backend(0.2)`（后端不提供 `spin_once` 时
退回 `time.sleep`，与原来逐字等价）。

> 注：同一类缺陷的第一处（bootstrap 重试）在本轮之前已修。两处的现场症状
> 分别是 `NO_LOCALIZATION` 与 `"compute path timeout"`，**都不像「没人 spin」**。

## 4. 范围外发现（均未擅自扩大改动）

### 4.1 只规划模式走不出一个完整导航周期——**是这套模式的定义，不是缺陷**

`execution_enabled:=false`（默认；`ENABLE_MOTION=0` 时由 `start_nav2_autonomous_search.sh` 选择）
**只起 planner_server + bt_navigator + 坐标桥**，controller_server / velocity_smoother /
collision_monitor 一个都不起（launch 自己的日志第 3 行写明）。三方一致（`ps`、`ros2 node list --no-daemon`、
launch 日志）。

计划书 §7.4 要求限速必须真写进 RPP 的 `FollowPath.desired_linear_vel` 才肯发 `NavigateToPose`；
没有控制器可写 ⇒ 每个候选被 `REJECT_NAV2_NOT_READY` 拒掉：

```
"corridor speed limit 0.056~0.093 m/s could not be applied to controller_server"
```

**走廊分析本身是成功的**（§2.1），被拦下的是「发速度」那一步。要看端到端导航验收，
必须用 `execution_enabled:=true` 重启 bringup——launch 文档写明那是「用户现场验收后才由用户自己改为 true」。

### 4.1.1 执行模式已由用户授权启用（2026-10-08 下午），并暴露一个真缺陷

用户当日给出运动授权后，用 `scripts/go2w/start_nav2_autonomous_search.sh --enable-motion`
起了执行模式（`configs/go2w/navigation_gate.yaml` 的 `nav2_allow_execute` 临时置 `true`，
验收结束后**已还原为 `false`**，sha256 `eae57bdb…6eb0bf61` 与改前逐位一致）。

**第一次起是失败的**，而且失败的样子很容易看错：`[lifecycle_manager_navigation]:
Failed to bring up all requested nodes. Aborting bringup.`，但
`planner_server` 与 `controller_server` **已经 active**，只有
`behavior_server` / `bt_navigator` / `velocity_smoother` / `collision_monitor`
停在 inactive。只查前两个节点会判成"起来了"。

真因在 `bt_navigator`：**Humble 的 `on_activate` 会把两棵默认树都先解析一遍**
（`default_nav_to_pose_bt_xml` 与 `default_nav_through_poses_bt_xml`）。本项目只填了前者，
后者落在库存的 `navigate_through_poses_w_replanning_and_recovery.xml` 上，那棵树含 `BackUp`，
而 `nav2_params_humble.yaml` 的 `behavior_plugins` 出于安全**刻意只注册了 `[spin, wait]`**
（backup / drive_on_heading / assisted_teleop 会让机器人在走廊分析之外产生位移）。
于是激活阶段：

```
[bt_navigator]: "backup" action server not available after waiting for 1.00s
Exception when loading BT: Action server backup not available
Error loading XML file: .../navigate_through_poses_w_replanning_and_recovery.xml
```

**改法（最小）**：把这棵树也绑到同一棵按模式选出的 XML 上
（`ros2_ws/.../launch/robot_scene_nav2.launch.py` 的 `through_poses_bt = navigation_bt`）。
本项目从不发 `NavigateThroughPoses`，这棵树只需要能被构造出来；两棵自带的树都不含
`BackUp` / `Spin`，绕开了 `behavior_server` 的依赖。

中途我先试过两条**错的**路子，都留档以免重走：给 `plugin_lib_names` 补 4 个 BT 库
（只把报错从 `RemovePassedGoals` 推进到 `backup`）、以及把 `EXECUTE_NODES` 重排成
`behavior_server` 在前（完全无效——`/backup` 这个 action server 压根不存在，
不是顺序问题）。两条已**全部还原**，`EXECUTE_NODES` 与 `plugin_lib_names` 都是原文。

**修好之后的实测**：六个生命周期节点全部 `active [3]`
（`planner_server` `controller_server` `behavior_server` `bt_navigator` `velocity_smoother`
`collision_monitor`），`/go2w/nav2_cmd_vel` 有 **1** 个发布者（只规划模式下是 0），
bringup 日志 **468 行里只有 1 行 ERROR**（那行是 `controller_server: Failed to make progress`，
属于 4.1.2 里那次真的派发了目标之后的正常结果，不是启动缺陷）。

### 4.2 global_costmap 曾连续丢弃 316 帧扫描（偏移恒为 91.0 s），随后自行停止

### 4.3 图上的 `/controller_server/set_parameters` 是僵尸广告

`ros2 service list --no-daemon` 与节点的 `get_service_names_and_types()` 都能看到
`/controller_server/set_parameters [rcl_interfaces/srv/SetParameters]`，但**没有 `/controller_server` 节点**
（`ros2 node list --no-daemon` 里没有）。两个佐证：

1. 真 rclcpp 节点会广告 **6 个**参数服务（get / list / describe / set / ±atomically），这里只有 **1 个**；
2. 实测 DDS 请求 **6 s 无应答**（`service_is_ready()` 恒 False），而同样最小路径对
   `/planner_server`、`/bt_navigator`、`/plain_slam_health_monitor` 都是 `ready=True` + call OK。

**因此绝不能把 `service_is_ready()` 「修」成「图上有没有这个名字」**——那会让搜索在限速没写进去的情况下
照发 `NavigateToPose`。现有判据是对的。

### 4.4 一个孤儿的 `lifecycle_manager_plan_only`

`ros2 node list` 里 `/lifecycle_manager_plan_only` 出现**两次**，`ps` 佐证是两个进程
（pid 168786 跑了约 69 min，pid 176226 约 45 min）。`start_nav2_autonomous_search.sh` 的 `stop_owned`
按 pidfile 停，只停得掉当前那套。零运行时影响（都只是 lifecycle manager），但会让 `node list` 的读法出错。

### 4.5 更正我自己先前的一个结论：`_classify_empty_candidates` 的 `getattr` **无观测效应**

我先前说过「`_classify_empty_candidates` 对 frontier **dict** 用 `getattr(item, "status")`，
会高估可达 frontier」。**这句是错的**，更正如下：

- frontier 确实是 dict（`app/spatial/semantic_navigation_graph.py:53` 的 `dict[str, dict[str, Any]]`），
  `getattr` 对 dict 永远取不到属性、恒返回默认值——这半句成立；
- 但**全仓没有任何一处把 frontier 的 `status`/`state` 从 `"OPEN"` 改走**（唯一写入点是创建时的字面量），
  所以 `getattr` 与 `.get` 今天算出来的三个计数**逐位相同**，`reachable` 并不会被高估。

结论：**今天不动它**（改动落最小处）。它是一个只有将来有人开始更新 frontier 状态时才会咬人的潜伏写法，
届时 `_candidate_plan_context`（`autonomous_explorer.py:1760` 用 `entry.get("status") or entry.get("state")`）
与它就会分叉。

### 5.3 原因 B：`cancel()` 不让出 `_active`（已修）

现场时序（`decisions.jsonl` + `events.jsonl` 逐条对上）：

```
cycle 1  local_001  → navigation_result status=timeout
                      "navigation wait timeout after 15s"
cycle 2  local_002  → status=rejected  "nav2 backend already has an active goal"
cycle 3  local_003  → status=rejected  "nav2 backend already has an active goal"
```

`autonomous_explorer.py:1264` 在 `TIMEOUT` 后调 `self._backend.cancel(handle)` 准备重试，
但 `Nav2SearchBackend.cancel()` **只填了 `handle.result`、没清 `self._active`**。
唯一会清 `_active` 的两处是 `get_navigation_status` 的 `:603` 与 `_finish_canceled` 的 `:822`；
而 `:587` 对已结算的 handle 会**提前 return**，`:603` 永远走不到。
于是从第 2 轮起，`execute_goal` 一律在 `:518` 被判 `GOAL_IN_FLIGHT`，
`ComputePathToPose` 一次都没再发过。

**离线复现**（用仓库自带假 Action server，`/tmp/probe_cancel_wedge.py`）：

```
goal1 已发 NavigateToPose;  active = True
cancel 后 handle.result = cancelled
cancel 后 active       = True   <-- 关键
goal2 结果            = rejected / nav2 backend already has an active goal
goal2 规划请求数      = 1 （应为 2）
```

**改法**：在 `cancel()` 结算 handle 的同一个 `if` 里补 `self._active = None`
（与 `_finish_canceled` 对齐）。**注错校准**：把那句换成 `pass`，
新增的 `test_cancel_frees_the_slot_for_the_next_goal` 唯一 fail、同文件其余 34 条全过
（`1 failed, 34 passed`）——原有 cancel 用例只查 handle 是否被结算，**查不出槽位没让出来**。
还原后 sha256 逐位一致（`6c68f894…4bf64e734`），35 passed。

> 这一条与 `nav2_search_backend.py` 里的 TF 位姿那两条（§1.1）是**不同**的缺陷，
> 只是同一个文件。它的现场症状（一串"已有活动目标"）看不出是"取消没让位"。

### 5.5 五道闸门的接线（2026-10-10，代码已落地，**同日真机验证通过**）

用户 2026-10-10 指示「按你推荐的来改」。选定的方案是**「跨岛桥 + 把服务包成话题」
合在同一个地方做**，落点是 `motion_network_proxy.py` —— 它是这套设计里**唯一**
既看得到机器人本地状态、又活在网络图上的进程（launch 里只有它和
`network_low_state_capture` 显式 `ROS_LOCALHOST_ONLY=0`）。

链路：**动作服务器（本地图） → `motion_local_gateway` 新 `op:"state"` → Unix socket
→ `motion_network_proxy` 轮询 → 五个 Bool 话题**。

| 闸门 | 取值来源 | 性质 |
| --- | --- | --- |
| `operator_not_armed` | 网关按动作服务器那条 **60 s 空闲武装租约**（`CheckArmTimeout`）重建，由它转发的每次 arm 应答与每个运动 goal 驱动 | **重建**，非读数 |
| `lease_unavailable` | 网关读 `GO2W_LEASE_STATUS_DIR` 下的 `alive`/`id`/`heartbeat`，与 `lease_status_bridge.py` **同源同规则** | 测量 |
| `robot_error_or_unknown` | 网关订阅 `/go2w/motion/local_sportmodestate` 的 `error_code`，**只在新鲜时**判 0 | 测量 |
| `emergency_stop` | 网关在 `/go2w/local_emergency_stop` 成功时**锁存**；没有任何东西会自动清它，与 `HandleEmergencyStop` 把 `armed_` 置 false 同义 | 锁存 |
| `remote_override` | **没有来源**，见下 | **断言** |

**为什么 `software_arm` 是重建也安全**：动作服务器自己的
`GoalContext{!require_arm || armed_}` 才是权威。乐观的 `software_arm` 最多让 bridge
把 goal 发出去，然后被服务器按 `require_arm` 拒掉 —— **门是纵深，不是唯一一道**。
`robot_error_zero` 同理（服务器还会查 `state.error_code != 0`）。

**`remote_override` 是唯一一个不可测的输入**，所以这里不猜：
`configs/go2w/navigation_gate.yaml` 自己就写着「Runtime health fields must come from
live ROS observations, **never operator assumptions**」。默认**保留拦截**，只有操作员
显式传 `remote_override_cleared:=true`（`start_motion_control` 那条 launch 参数）才放行；
传了会在每次状态变化时打印一行把它标成 asserted。**这一条要不要放行是操作决策，
不是代码决策。**

**为什么不是新建一个宿主侧发布者**：真实状态全在机器人本地图上，宿主侧发的任何值
都只能是编的；而重复发布者是真风险（`lease_status_bridge.py` 也在发

**两条操作纪律**（本轮踩到，已记进记忆）：
重启单个 ROS 节点时 `ros2 run` 是**两层进程**，只杀包装层会留下**孤儿节点**继续发布，
再起一个就是**两个发布者互相覆盖**；`pkill -f 'ros2 run ...'` 还会匹配到**自己这条命令行**
把 shell 一起杀掉（退出码 144）。正确做法是用 `/proc/<pid>/exe` 枚举 + 启动时间分辨
包装层/节点/历史残留。
