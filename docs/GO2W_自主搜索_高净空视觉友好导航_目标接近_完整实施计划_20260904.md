# 0. 给执行 AI 的硬性指令

执行本计划时，必须遵守以下规则。

1. **不要推倒重写现有架构。** 优先复用已经存在的：
   - `DepthObjectLocalizer`
   - `RecoveryManager`
   - `recovery_motion.py`
   - dual-LiDAR evidence / observability / navigation gate
   - `SemanticNavigationGraph`
   - `long_term_goal_selector.py`
   - `ExplorationGraph`
   - `Go2WExperimentalBackend`
   - 现有 WebUI event / decision record / pytest 基础设施。

2. **不要让 LLM 成为实时碰撞安全控制器。**
   - LLM 只能提供语义偏好、frontier/place 排序、是否需要恢复/接近的高层意图。
   - LiDAR、footprint、clearance、swept-volume、breadcrumb 和运动执行结果才是安全真值。
   - 任意 LLM 输出必须可以被 deterministic safety layer 否决。

3. **不要把“即将撞击时停车”和“自动绕障”混为一谈。**
   当前 Go2W backend 的事实是：
   - `supports_platform_obstacle_avoidance=False`
   - 计划中的底层碰撞停车未来可以实现，但当前不能假定已经存在。
   - 新系统必须在**规划阶段**主动避开墙边、桌角、狭窄死角，而不是依赖即将碰撞时才停止。

4. **优先让机器人走高净空区域，而不是只追求最短路径。**
   - 窄门/窄通道仍然可以通过，但只有在没有更高净空替代路线时才走。
   - 普通开放走廊应自然偏向走中间。
   - 靠墙路径应产生连续增加的 cost，而不是“只要没撞就是同样好”。

5. **Frontier 不是机器人的最终 pose。**
   Frontier 只是“值得探索的边界/区域”；机器人真正导航到的是经过安全和视觉质量优化后的 `ViewpointCandidate`。

6. **视觉确认目标不再等于任务结束。**
   除非配置明确要求 legacy 行为，否则：
   - `TARGET_CONFIRMED` 只是切换到目标接近阶段。
   - 必须进一步定位目标、生成安全 standoff viewpoint、接近、重新观察和最终验证。
   - 只有达到最终距离/朝向/视觉/安全条件后才能 `TARGET_REACHED` / `TARGET_FOUND`。

7. **后退仅用于 recovery，不作为常规探索动作。**
   - 后退必须优先复用现有 breadcrumb-safe reverse。
   - 未有可信后向空间证据时，禁止盲目后退。
   - 正常规划优先从根本上避免进入墙角；Recovery 是最后的脱困机制。

8. **所有新增策略必须可配置、可记录、可测试、可关闭。**
   - 默认配置必须保守。
   - 关键决策必须进入 event / decision record，能在 WebUI 或日志里追踪为什么选了这个 viewpoint/path/recovery。

9. **禁止把当前不可靠的全局 LIO 地图当作唯一安全真值。**
   - Fresh local LiDAR = 近场安全真值。
   - breadcrumb / odom = 短时 recovery 依据。
   - topology/frontier = 搜索结构与长程方向。
   - LIO/global metric map 只有在 freshness/quality 合格时才参与 metric route；质量不足时必须降级。

10. **完成标准不是“代码能 import”。**
    最终必须：
    - 新增/修改单元测试；
    - 跑现有相关回归测试；
    - 跑新增端到端 mock 场景；
    - 给出真机 dry-run / observe-only / supervised-motion 验收步骤；
    - 不破坏现有 operator stop / safety gate / backward breadcrumb tests。

# 1. 改造目标

本次整改统一解决以下四类问题。

## 1.1 探索时尽量走“中间”和开放区域

目标不是几何意义上强制走走廊中心线，而是让路径优化主动偏好：

- 离墙、桌子、柜子、设备等障碍物更远；
- 机器人完整 footprint 与障碍保持更大 margin；
- 路径全程最小 clearance 更大；
- 转弯 swept volume 更宽松；
- 相机前方有更大有效观察空间；
- 更少把相机正对近距离墙面/桌面/大平面；
- 即使略微绕远，也优先高净空、高可观测路径。

## 1.2 卡住时能理解“为什么看不到”，并真正脱困

现状中“连续无信息”可能是：
- 已经搜尽；
- 摄像头贴墙；
- 视角被家具遮挡；
- 机器人虽然执行命令但无有效进展；
- LiDAR/地图 stale；
- 反复选择相同低质量 viewpoint。

整改后必须区分这些状态，并在几何阻塞时：

`STOP -> safe backward recovery -> REOBSERVE -> replan`

而不是单纯把 `RECOVER` 当成 replan 标签。

## 1.3 大模型参考更多 embodiment state

LLM 不接收原始点云，而接收压缩、结构化、可解释的：

- local LiDAR clearance sectors
- front/rear/left/right clearance
- swept-volume safety summary
- sensor freshness / observability
- robot pose quality
- Place / Frontier topology
- frontier route cost / route clearance
- recent failure / recovery context
- perception quality

LLM 负责**高层搜索偏好**，不负责底层避碰。

## 1.4 找到目标后尽量安全接近，而不是远处看到就结束

最终行为应变为：

`SEARCH -> VERIFY -> TARGET_CONFIRMED -> LOCALIZE_TARGET -> PLAN_APPROACH -> APPROACH -> FINAL_OBSERVE -> FINAL_VERIFY -> TARGET_REACHED`

接近原则：

> 在安全、可达、目标持续可见、RGB-D 深度可信、相机视角良好的约束下，尽可能靠近目标，并在合理 standoff 范围停止。

# 2. 已确认的当前代码问题与必须修复的接口

以下内容必须先修，不能跳过。

## 2.1 `REVERSE` 与 `BACKWARD_RECOVERY` 动作词表不一致

当前：

- `Go2WExperimentalBackend` 发布 primitive：`BACKWARD_RECOVERY`
- `candidate_goal_generator._goal_primitive_allowed()` 对 `relative_dx < 0` 检查的却是 `REVERSE`

因此必须统一。

### 修改要求

在 `app/navigation/candidate_goal_generator.py`：

```python
if dx < -0.01:
    return "BACKWARD_RECOVERY" in allowed_primitives
```

不得再使用 `REVERSE` 作为该 backend contract。

同时新增回归测试，验证：

- `allowed_primitives={"BACKWARD_RECOVERY"}` 时 recovery negative dx 不被过滤；
- 仅 `FORWARD` 时 negative dx 被过滤；
- 正向仍只依赖 `FORWARD`。

### 推荐进一步收紧

不要让普通 candidate generator 主动产生负 `relative_dx`。

推荐新增明确语义常量：

```python
GOAL_RECOVERY_BACKUP = "RECOVERY_BACKUP"
```

如果改动范围太大，也可以继续使用 `GOAL_RELATIVE_MOVE + relative_dx<0`，但必须保证：

- 只有 `RecoveryManager` 能构造这类 goal；
- provenance 必须含：
  - `source="recovery_manager"`
  - `recovery_only=True`
  - `recovery_reason`
- `candidate_goal_generator` 不得把它作为普通 exploration candidate。

# 5. Clearance-aware 导航：让机器人主动远离墙边

这是本次整改的核心。

---

## 5.1 不要把“hard safety”和“preference”混在一起

必须有两层。

### Hard clearance

表示机器人 footprint + 安全 margin 不允许进入的区域。

当前硬件几何配置约：

- length ≈ 0.70 m
- width ≈ 0.43 m

因此第一版建议配置：

```yaml
hard_clearance_m: 0.40
```

该值必须可调，不能硬编码。

若某 pose/path 的 footprint/swept-volume 小于 hard limit：

```text
直接 reject
```

不能用权重去“抵消”。

### Preferred clearance

表示正常探索希望保持的距离。

第一版建议：

```yaml
preferred_clearance_m: 0.80
```

在 0.40–0.80 m 之间产生连续 cost；大于 0.80 m 基本不再惩罚。

---

## 5.2 新增 `clearance_map.py`

新增：

`app/navigation/clearance_map.py`

职责：

1. 接收当前可用 occupancy / local obstacle representation；
2. 对 free-space 计算 obstacle distance field；
3. 提供：
   - `clearance_at(x, y)`
   - `path_clearance(path)`
   - `pose_clearance(pose, footprint)`
   - `swept_clearance(pose_a, pose_b, footprint)`
4. 对 `UNKNOWN/STALE` fail-closed 或按策略高惩罚，不得默认 free。

如果当前全局 map 质量不足：

- 支持 local-only 模式；
- path 较长时只对当前可验证局部段计算；
- topology/global route 只提供方向，local motion 每一步重新验证。

### 距离 cost

建议：

```python
def clearance_cost(d, hard, preferred):
    if d is None:
        return UNKNOWN_COST
    if d < hard:
        return float("inf")
    if d >= preferred:
        return 0.0
    x = (preferred - d) / max(1e-6, preferred - hard)
    return x * x
```

---

## 5.3 路径总代价

新增或扩展 path scoring：

```text
J(path) =
    w_length      * normalized_path_length
  + w_clearance   * integrated_clearance_cost
  + w_min_clear   * min_clearance_penalty
  + w_turn        * turning_cost
  + w_unknown     * unknown_space_risk
  + w_view        * camera_view_risk
```

第一版必须让：

> 多绕 0.5–1 m 的高净空路线，通常优于贴墙的最短路线。

---

## 5.4 “走路中间”验收定义

不要使用“必须处在中心线”这种脆弱规则。

验收应使用 clearance：

对于宽度足够的走廊（例如 >1.5 m 可用宽度）：

- 规划路径的 `min_clearance` 应显著高于贴墙路径；
- 在左右对称、长度相近时，路径中心点应接近走廊中部；
- 不得出现无必要的墙边擦行。

## 7.2 Frontier 模式

输入一个 frontier 后，不直接使用 frontier centroid 作为机器人 goal。

围绕 frontier 生成多个可观测 pose：

- 沿 frontier normal 后退不同 standoff；
- 允许左右偏移；
- 允许 yaw 小范围调整；
- 每个 pose 计算：
  - local clearance
  - path clearance
  - view quality
  - information gain
  - route cost

选最佳 viewpoint。

---

## 7.3 Target approach 模式

围绕目标生成 approach ring。

建议第一版 angle sampling：

```text
-90, -60, -30, 0, +30, +60, +90 deg
```

只保留：

- free-space
- LOS 成立
- route 可达
- clearance 合格
- 最终相机朝向目标
- 目标距离在 standoff 区间

如果 global target position 不可靠，切换到 local visual-servo 模式，不做虚假的 map pose。

# 22. Target-aware obstacle handling

目标物体本身通常会被 LiDAR 视为障碍。

不能出现：

```text
想接近垃圾桶
-> LiDAR 看见垃圾桶
-> 前方有障碍
-> 永远不允许接近
```

---

## 22.1 正确约束

允许目标表面处于机器人终点前方。

但从当前 pose 到最终 standoff pose 的机器人 swept-volume 必须 free。

判断应接近：

```text
target obstacle distance ≈ RGB-D target depth
且
robot path only travels to target_depth - standoff
```

则目标本身不是 path collision。

其他 obstacle 仍正常阻挡。

---

## 22.2 不能简单忽略目标方向所有 LiDAR 点

这是危险的。

只允许在：
- target bbox/bearing/depth 与 LiDAR cluster 空间吻合；
- 且该 cluster 位于 standoff 之外；
时将其标记为 `target_surface`。

其他点仍是 obstacle。

如果第一版难以做 cluster association：
- 不要实现激进的点云忽略；
- 使用“计划步长永远小于 `depth - min_standoff` + local footprint gate”；
- 保守停止优先。

# 39. 故障降级原则

任何数据链故障必须 fail-safe。

| 故障 | 行为 |
|---|---|
| LiDAR stale | STOP / WAIT，不把未知当 free |
| LIO global pose 不可信 | 降级到 local LiDAR + topology qualitative |
| D435 depth 无效 | 不执行 target forward approach |
| target RGB only | reobserve，不生成真实 target distance |
| topology 空 | local frontier/fallback，但仍受 clearance gate |
| LLM 失败 | deterministic semantic/frontier fallback |
| Recovery breadcrumb 失效 | 不盲退 |
| path planner 无解 | replan / alternate viewpoint，不撞墙硬走 |
| 所有 recovery 都不可执行 | STOP + operator intervention / explicit failure |

# 45. 代码设计细节：hard gate 与 score 的边界

明确：

## Hard gate

下列条件任一成立直接 reject：

- footprint collision
- swept-volume collision
- clearance < hard
- required LOS false
- route unreachable
- stale/unknown geometry 且动作依赖该方向
- approach 无 fresh target depth（若配置 require）
- backward 无 safety evidence

## Score

只对已 hard-safe 的候选排序：

- semantic
- info gain
- novelty
- clearance preference
- view quality
- route length
- turn count
- failure memory

绝不允许：

```text
semantic score 很高
+
collision risk 很高
=
仍然获胜
```

# 53. 设计底线

本次整改最终必须形成以下行为原则：

> **语义层决定“哪里值得去”；拓扑层决定“从哪个区域到哪个区域”；Viewpoint Planner 决定“站在哪里看最好”；clearance-aware planner 决定“怎么走得离障碍更远”；LiDAR/footprint safety gate 决定“此刻能不能动”；Recovery 只处理预防机制仍未避免的极端卡死；目标确认后通过 RGB-D 和安全约束继续接近，直到真正达到可用的近距离观察位姿。**

这就是本次修改完成后的唯一目标架构。不要退回“LLM 直接发运动 + 快撞了再停”的模式。
